검증기가 `build.py` 를 import 해 그 결과를 기대값으로 쓰면, 검증하는 것은
"엑셀이 build.py 말대로 썼는가" 뿐이다. **build.py 의 선정 로직이 틀리면 전부 통과한다.**

2026-09-07 교원확보율에서 임용예정자 3명이 동명이인 오판으로 통째로 빠졌는데,
27,252건 검사가 전부 통과하고 **100.0점**이 나왔다. 세 학과 확보율이 틀린 채로.

더 나쁜 형태: 검증기가 "반영됐거나, 대상이 사유를 남겼거나" 를 통과 조건으로 두는 것.
원래 버그가 정확히 "사유를 남기고 빼는" 모양이라 고친 뒤에도 못 잡았다.
평가자가 구 버그 상황을 그대로 먹여 보고서야 드러났다.

**Why:** 계산 축([[verification-two-axes]])의 사각지대와는 또 다르다.
데이터가 깨끗해도, 대상의 **판단**을 기대값으로 삼는 순간 그 판단은 검증 밖으로 나간다.

**How to apply:**
- 누락·선정 검사는 **원자료에서 직접 재판정**한다. 대상 모듈의 함수를 재사용하지 않는다.
  (예: "건너뛴 임용예정자는 교원조회에 생년월일까지 같은 사람이 실제로 있음을 증명해야 통과")
- 집합 포함 검사를 넣는다: 원본의 산정대상 키 집합 ⊆ 산출물 키 집합.
- **점수를 건수로 희석하지 말 것.** 3명 누락이 27,252건 중 3건이면 99.99점 → 반올림 100.0.
  누락·통합문서 파괴는 건수와 무관하게 **즉시 0점**으로 떨어뜨린다.
- 새 검사가 장식이 아닌지 **결함을 일부러 주입해** 확인한다. 구 버그 상황을 그대로 재현해
  CRITICAL 이 뜨는지 보는 것이 가장 확실하다.
