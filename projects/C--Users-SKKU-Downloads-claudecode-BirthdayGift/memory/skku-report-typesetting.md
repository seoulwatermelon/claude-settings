SKKU 회의자료 hwpx를 만들 때 사용자가 지적한 조판 결함 4가지와 해결책. **`skku_report.Report`에 이미 반영되어 있으므로 그것만 쓰면 된다.** 직접 XML을 짜거나 별도 빌더를 만들지 말 것.

**Why:** 사용자 지적 원문 — "중간에 갑자기 공백이나 띄어쓰기가 되면서 가독성 떨어지고, 문단 첫머리 첫글자 앞에서 shift+tab의 들여쓰기 되어야 하는데 그것도 안되고 표에서는 맞춤도 안되어 있고 어떤 표는 다음 페이지에서 시작하고 지금 난장판이야."

## 4대 규칙

### 1. 들여쓰기는 문단 여백으로 — 문자열 앞 공백만으로는 안 된다
줄이 넘어가면 둘째 줄이 왼쪽 끝으로 돌아가 문단이 깨진다. **번호표지 뒤에 정렬(내어쓰기)** 되어야 한다.
`Report._p()`가 `left = em(들여쓰기공백 + 번호표지) × pt × 100`, `intent = -left`인 paraPr을 자동 생성해 `_inject_parapr()`로 header.xml에 써 넣는다. 계층별 실측값: `1.` 3750 / `1)` 4500 / `①` 4200 / `※` 3900.

### 2. 수동 줄바꿈 금지
1이 되면 한글이 알아서 접는다. `_chop()`·`_protect()` 같은 수동 자르기를 넣으면 **줄 중간에 공백이 박히고 고아 행이 생긴다.** 사용자가 말한 "갑자기 공백"의 원인이 이것. 대신 `Report`의 줄 폭 경고(15pt 40em/줄)를 보고 **문장을 짧게 고쳐 쓴다.**

### 3. 표 셀은 열별로 정렬을 지정한다
`table(rows, widths, aligns=...)`의 `aligns`를 생략하면 전부 JUSTIFY로 나와 숫자가 삐뚤어진다.
`18`=가운데, `0`=왼쪽. 라벨 열은 왼쪽 또는 가운데, **숫자·금액·인원 열은 가운데**로 명시할 것.

### 4. 표 제목은 표와 같은 쪽에 — `caption()` 사용
`【 표 제목 】`을 일반 문단으로 쓰면 제목만 앞 쪽에 남고 표가 다음 쪽에서 시작한다.
`Report.caption('【 … 】')`은 `keepWithNext=1` 문단모양을 써서 표와 붙여 놓는다. 표 제목에 `l2()`를 쓰지 말 것.

## 점검
빌드 후 확인 — 본문 문단이 100번대 paraPr을 참조하는가 / 셀 paraPr에 18이 섞여 있는가 / `caption` 문단이 `keepWithNext=1`인가 / 줄 폭 경고 0건인가.

## 5. 한 줄에 들어가는 길이 기준 (실측)

사용자 지적 — *"몇글자 때문에 줄 바뀌어서 줄추가 되는 건 기준 세워서 한 줄에 들어가도록. 그 조금 때문에 줄 띄기 한게 티가 나"*

`skku_report.py`의 옛 상수 `C15 = 40.0`은 실측보다 **25% 관대**해서 「줄 폭 경고 없음」이 거짓으로 떴다. 실측 물리 계산으로 교체했다.

```
1줄 수용량(em) = 169.98mm ÷ (글자크기pt × 0.3528mm) × 0.96
```

| 글자크기 | 1줄 한도 | 용도 |
|---|---:|---|
| 16pt | 28.9em | 대분류 `1.` |
| 15pt | **30.8em** | `□` · `-` |
| 14pt | 33.0em | `·` |
| 13pt | 35.6em | `※` |
| 12pt | 38.5em | 표 셀 |

표 셀은 `cell_cap(열너비HWPUNIT)`로 별도 계산.

**초과 시 처리 순서** — ① 다중 출처는 `※` 두 줄로 분리 ② 문장 축약 ③ 긴 나열은 표로 ④ 주소는 파일명만.
**절대 금지**: 줄을 손으로 자르거나 개행문자를 넣는 것(규칙 4와 충돌 — 중간 공백·고아 행 발생).

빌드 후 `verify_layout.py`로 확인. `validate.py`는 구조만 보고 레이아웃은 안 본다.

## 6. 판본 식별은 빌더 `.py` 해시로 — hwpx 해시는 못 쓴다

hwpx는 ZIP이고 **각 항목에 빌드 時刻이 박힌다.** 내용이 한 글자도 안 바뀌어도 分이 넘어가면 MD5가 달라진다(같은 分 안 연속 빌드는 동일). 실제로 한 검토 회차에서 본문이 전부 같은데 해시가 4번 바뀌었다.

- 평가자·협업자에게 판본을 알릴 때는 **`build_*.py`의 MD5**를 준다. 빌더는 결정적이다.
- 내용 동일성을 직접 비교하려면 `Contents/section0.xml`·`header.xml`의 해시를 본다.
- 파일 크기도 1B 정도 흔들릴 수 있다(ZIP 시각 인코딩).

## 7. 분량을 줄일 때는 「무엇이 그 줄에 의존하는가」를 먼저 본다

쪽수를 맞추려 줄을 덜어낼 때 실제로 두 번 구멍이 났다.

- **도출 가능성과 읽는 순서는 별개다.** 「뒤 章의 표에서 도출 가능」하다고 앞 章의 註를 지우면, 읽는 사람은 그 지점을 근거 없이 지나간다(같은 쪽에 9名·8名이 나란히 놓인 사고).
- **전제 줄을 덜어내고 결론만 남기면 출처가 뜬다.** 출처가 말하지 않은 문장에 출처가 걸린 모양이 된다. 이때는 출처를 지우지 말고 **문장을 출처가 실제로 말하는 내용으로 고친다.**

## 8. docx 표를 읽을 때는 `gridSpan`(셀 병합)을 반드시 복원한다

`<w:t>` 텍스트만 평탄화해 뽑으면 **병합된 셀이 1칸으로 줄어** 행마다 칸 수가 달라지고, 열을 잘못 짝지어 **숫자를 정반대로 읽게 된다.**

실제 사고 — 리텐션 예산표에서 인원 행(8칸)과 금액 행(13칸)을 1:1로 짝지어 「'27年 2名·1人 1.50억」이라 결론냈으나, 인원 셀이 전부 `gridSpan=2`(2개 연도씩 병합)여서 실제로는 **「'27年 1名·1人 年 3억원」**이었다. 복원하면 전 구간에서 `금액 = 인원 × 3억`이 성립하고 누적 합계와도 맞았다.

**점검법** : 행마다 칸 수를 세어 헤더와 다르면 병합이 있는 것이다. 그리고 **표 안의 산식이 전 구간에서 성립하는지**(여기서는 금액÷인원이 일정한지) 반드시 검산한다. 산식이 깨지면 읽기를 틀린 것이다.
